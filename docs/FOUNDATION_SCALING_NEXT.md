# После проверки Foundation 3: устранение ограничений

Это технический проект продолжения Foundation 3, не новые игровые правила. **Обновление 13 сентября:** первый срез состояния/архива реализован как Checkpoint 1; фактические границы — [IMPLEMENTATION_CHECKPOINT_1.md](IMPLEMENTATION_CHECKPOINT_1.md), проверки — [STATUS_CHECKPOINT_1.md](STATUS_CHECKPOINT_1.md). Выбрана доверенная локальная контрольная точка. Чтение только видимой страницы и очистка архива ещё не сделаны. Ниже сохранены исходное обоснование и дальнейшие предложения; они не означают, что все пункты уже реализованы.

## 1. Состояние кампании отделить от полного воспроизведения истории

Дополнение Runtime 2: убрано повторное восстановление на загрузке; список кампаний использует текущий мир без архива; экран журнала запрашивает страницу; цикл публикации обрабатывает новые блоки. Полная проверка архива выбранной кампании сохраняется. Проверки контейнеров переведены на общий подсчёт. Подробности: [STATUS_RUNTIME_2.md](STATUS_RUNTIME_2.md).

Сейчас `Sm2JourneySession.restore` создаёт начальный мир и заново применяет всю историю. `Sm2JournalView` и `Sm2ExpeditionView` повторяют её для своих данных. Сохранение через `Sm2CampaignStore` тоже включает восстановление и проверку. Такая модель удобна для проверки короткого примера, но цена каждого чтения растёт вместе с прошлым.

Следующий рабочий срез должен ввести проверяемый снимок текущего состояния с независимым декодером мира. Он проверяет анатомию, предметы, владельцев/контейнеры, развитие, Душу, места и активную встречу теми же правилами. Проверка структуры и согласованности состояния не должна требовать исполнения всех прошлых действий. Нельзя просто довериться хешу JSON: хеш подтверждает целостность, а не законность состояния.

История становится последовательностью ограниченных блоков. Закрытый блок имеет стабильный ID, порядок, диапазон ревизий, версию и хеш; текущий снимок ссылается на согласованный набор. Журнал читает страницы блоков. Факты выполненного похода и полученной практики должны фиксироваться на принятых переходах и переживать архивирование; UI не выдаёт награды. Повтор действий остаётся отдельным диагностическим режимом.

До реализации выбрать и проверить точную политику: сохраняем ли полную проверяемую цепочку происхождения снимков либо допускаем доверенную локальную контрольную точку. Это техническая граница гарантии, её нельзя скрыть за прежним словом «проверено».

## 2. Совместимость и безопасная публикация

Новый формат отдельный. Старый Survival 3 сначала полностью проверяется прежним загрузчиком, затем переводится в новый снимок и сравнивается по фактам мира/похода/журнала. Исходный файл остаётся доступен до успешной проверки нового. Ошибки записи, отсутствующий блок, неверный порядок, повреждение, несовместимая версия и прерванная публикация не должны оставлять слоты в смешанном состоянии.

Приёмка: длинная кампания с боями, ранениями, доставкой, смертью и новым телом; откат к более раннему сохранению; восстановление `.bak`; отказ не меняет живую сессию и предыдущий рабочий комплект файлов. Целевые задержки и нагрузки фиксируются до реализации.

## 3. Массовый контент

Версионированный пакет определений и общий индекс стабильных ID. Авторские файлы могут быть разбиты по направлениям/наборам; дубликаты и ссылки проверяются после сборки пакета. Поведение хранится в ограниченном наборе операций, данные не содержат исполняемые строки. Контрольная сумма относится к проверенному пакету.

Каталоги после сборки доступны только через отделённые значения/запросы. Индексы предпосылок, зависимых узлов и источников эффекта строятся один раз. Новый профиль с пределом выше 1000 потребует проверки тела с изученными узлами и сохранения, а не только замены константы парсера.

## 4. UI больших деревьев

Запрашивать выбранное направление и видимую страницу, а не формировать карточки всего каталога на каждое открытие. Поиск, переход к предпосылкам, покупка со старой ревизией, собственная практика и бонусы улучшений должны сохранять текущую семантику. Отдельно измерить кадры/число Controls и задержки на 1000/10000 узлов. Граф без UI этого не доказывает.

## Порядок

Сначала снимок/история/сохранения с переносом прежней кампании, затем больший пакет контента и ограниченная по объёму выдача данных UI. Доводка визуальной сцены остаётся этапом 4; перед расширением механик на этапе 5 — ручной просмотр пользователя. Эти будущие изменения не входят в результаты текущей проверки.
