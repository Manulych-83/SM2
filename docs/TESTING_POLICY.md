# SM2 — выбор проверок

Цель: проверять изменённое поведение и его связи, повторно использовать готовые инструменты. Это политика выбора, а не утверждение, что каждый перечисленный набор уже выполнен на текущем коде. Конкретные результаты — в отчёте задачи.

## Объём

- Документы без игровых изменений: проверить ссылки/согласованность/`git diff --check`; не экспортировать игру.
- Локальное исправление: тест поведения и затронутой связи. Простой текст/отступ не требует нового теста, повторяющего реализацию.
- Общие доменные правила, декодер, сохранения: набор системы + пользователи общего контракта + отрицательные случаи/повтор/совместимость по характеру изменения.
- UI: соответствующий настоящий графический тест и осмотр изменённого экрана. Headless не доказывает визуальное поведение.
- Законченный этап: один итоговый проход по затронутым системам. При изменениях ядра или перед широкой приёмкой — расширить регрессию; `all` доступен, не удалён. После успешного прохода не повторять без изменений/ошибок/нерешённого риска.
- Экспорт — когда нужно отдать обновлённую запускаемую сборку; проверять её запуск. Изменение только документации не повод пересобирать EXE.

## Карта наборов

| Изменение | Core `run_checks.ps1 -Suite` | UI `run_ui_checks.ps1 -Suite` |
|---|---|---|
| Главное меню, список актуальных примеров | `campaigns` при изменении загрузки | `start_menu`; `creatures`, `sequences` при изменении их входов |
| Хранилище, checkpoint, архив | `campaigns`, `checkpoint`, `expedition` | `campaigns`, `journal`, `start_menu` |
| Рост/оплата узлов/профиль | `after_battle`, `combat_profile`, `skill_scale`; нужный `p*` для старого формата | `development_layout`, `battle_results`, `skill_scale` |
| Общие правила/боевые эффекты | `rules`, `m4_effects`, `sequences`; атакующие/псионические наборы по затронутым вызовам | `rules`, `sequences` |
| Типы существ и встречи | `world_creatures`, `creatures`; `campaigns`/`checkpoint` для версии мира, `m4_effects` для общей сборки боя | `world_creatures`, `creatures`; `start_menu`, `campaigns` для входов |
| Физические предметы/тело | `content_packages`, `survival_tissues`, `survival_devices` | `inventory_layout`, `survival_tissues` |
| Экран персонажа и его связи | домен не затронут; при изменении вычислений — набор соответствующей системы | `character`, `inventory_layout`, `camp_layout`, `controls` |
| Домашний инвентарь, страницы и карточки | при изменении правил — `survival_tissues`, `survival_devices`; при оформлении домен не затронут | `inventory_home`, `inventory_layout`, `character`, `camp_layout`, `controls`, `expedition` |
| Лагерь/поход/переходы | `expedition`, `journey_guide` | `camp_layout`, `expedition` |
| Настройки/клавиши | домен не затронут | `settings`, `controls`; `display` для режима окна |
| Общая инфраструктура/границы слоёв | `unit`, нужные интеграционные наборы; при широком влиянии `all` | пользовательские потоки затронутых областей |

Это стартовый выбор. Не сокращать необходимое покрытие, если общий вызов затрагивает больше систем. Авторские каталоги: `tools/check_content.ps1`; большие стенды запускать при изменениях алгоритма/лимитов, не после каждой косметической правки.

## Запуск и результаты

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/run_checks.ps1 -Suite creatures
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/run_ui_checks.ps1 -Suite start_menu -OutputDirectory .local/ui-reports/my-change
```

Новая папка отчёта для каждого UI-прогона. Обёртки сохраняют полный лог и проверяют код завершения, положительное число проверок и отсутствие ошибок; в выводе достаточно сводки/пути. Не менять ожидаемые исходы ради прохождения.

Исторические UI-наборы `m*`, `p*`, `survival`, `survival_devices`, `display`, `battle_feedback`, а также отдельные примеры `creatures` и `sequences` автоматически включают прежнее меню в своём изолированном процессе. Для другого набора при необходимости явно указать `-LegacyDemos`. `start_menu` и `campaigns` проверяют новое обычное меню. Смена видимости не отменяет тесты старого домена/слотов. Некоторые исторические тесты могут содержать устаревшие требования к старому главному экрану (например P5 menu); их успешность без запуска не утверждать.

Промежуточные данные оставлять в `.local`. Итог: один `outputs/<этап>/summary.json` или краткий документ со списком запусков, passed/exit, числом проверок, путями доказательств и непроверенными границами. Сохранять нужные итоговые отчёты/изменённые экраны, не дублировать все удачные прогоны. Сборка в `builds/` не коммитится.
