# Foundation 3 — результат проверки фундамента

12 сентября 2026 · **0.8.22-foundation.3**, Godot 4.7.2, Windows, Intel Core i7-14700.

**Проверка выполнена; готовность к большой кампании не подтверждена.** Инструменты и безопасные оптимизации каталога внедрены. Длинная история восстанавливается без потерь, но время загрузки/записи и чтения экранов не укладывается в заранее заданные ориентиры. Следующий приоритет — снимок состояния и архив истории, затем массовый контент и UI.

## Изменения

- Итеративная проверка графа O(V+E) вместо многократного просмотра оставшихся узлов и линейного поиска зависимостей.
- Ленивая контрольная сумма неизменяемых данных каталога; сброс только после успешной пересборки. Возвращаемые определения и исходные данные отделены от принятого каталога.
- Проверка полного JSON-каталога с адресами повторных ID, отсутствующих предпосылок и циклов. Основной валидатор остаётся обязательным.
- Воспроизводимый стенд на реальных командах и существующем CampaignStore; корректность и масштабируемость имеют разные результаты.

Форматы сохранений, игровые определения, правила прогрессии и значения fingerprint сохранены. У основной кампании 15 узлов; тестовые тысячи не добавлены в игру. Состояние тела с 1000 изученными узлами прошло восстановление через действующие правила. Для 10000 проверен только алгоритм графа, не полный каталог/экран/кампания.

## Замеры

Базовый процесс запущен до оптимизации каталога, итоговый — с новым кодом. Отчёты: [baseline](../outputs/foundation-3/baseline/report.json), [verified](../outputs/foundation-3/verified/report.json), рядом журналы команд/коды завершения. Для каждого использован отдельный новый runtime. Прогоны частично перекрывались друг с другом и короткими проверками; это диагностическое сравнение отдельных запусков, не изолированная статистическая оценка производительности ПК.

| Операция | До | После |
| --- | ---: | ---: |
| Сборка/проверка обратной цепочки 1000 узлов | 829,456 мс | 9,973 мс |
| 100 повторных чтений уже вычисленной контрольной суммы, 1000 узлов | 1107,354 мс | 0,028 мс |

Первое вычисление контрольной суммы находится вне замера повторных чтений. Отдельный граф из 10000 узлов после изменения: **19,119 мс**. Существующая схема отклоняет каталог из 1001 узла с `progress_content_group`; ограничение намеренно не ослаблено.

Итоговый код, истории только из настоящих безопасных переходов:

| Переходы | Restore в памяти | Журнал | Цель, первый запрос | Сохранение | Загрузка с диска |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 1,530 с | 1,557 с | 1,531 с | 3,112 с | 3,108 с |
| 1000 | 14,664 с | 14,725 с | 15,208 с | 29,652 с | 29,879 с |
| 4096 | 60,280 с | 61,815 с | 63,555 с | 132,557 с | 112,653 с |

Все три состояния прошли настоящий дисковый round trip с равными хешами. Повторный запрос цели на том же снимке: 13,548 / 42,279 / 174,557 мс соответственно; даже кэш требует хеширования полного снимка. Запросы не меняют живую сессию. Повреждённая первая команда истории отклоняется без замены прежнего мира. После 4096 переходов следующая команда отклоняется атомарно.

Данные при 4096 переходах: **696149 байт JSON payload, 43438 значений дерева**, против ограничений 8 МиБ и 50000 значений. Этот случай сохранился; переполнение хранилища на нём не воспроизводилось. Истории с боями, большим количеством тел/предметов будут иметь другой размер и стоимость. Память процесса в конце: 64284670 байт; это не пик потребления.

Оба отчёта: `passed: true`, `ready_for_large_campaign: false`, 16 записей в `blockers`. Корректность восстановления подтверждена; превышение временных ориентиров и ограничения масштабирования не замаскированы нулевым кодом диагностического стенда.
